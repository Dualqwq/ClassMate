# 算法内容理解回答模板

## 使用条件

当学生不是在索要完整题解，而是在问下面这类问题时使用本模板：

- “这个算法到底在干什么？”
- “为什么要这样做？”
- “这一步为什么可以确定？”
- “我会背代码，但看不懂过程。”
- “这两个算法有什么区别？”

请求类型仍使用 `concept_explanation`。如果学生面对具体作业完全没有思路，则使用 `problem_hint`，并遵守提示层级；不要因为检索到了算法知识就直接泄露完整题解。

## Algorithm Understanding

按下面顺序回答，并根据问题删去无关部分：

```markdown
可以先把 <算法名> 理解成：<一句话说明它解决的问题>。

### 为什么会想到这样做

<普通方法的困难，以及算法的核心直觉。>

### 它一直记住什么

- `<状态或数据结构>`：<它代表什么>
- `<不变式或已确定集合>`：<算法每一步都保证什么>

### 用一个小例子走一遍

<选择最小但能体现关键转折的例子，逐步展示状态变化。>

### 为什么这一步不会错

<用初学者能理解的方式解释关键正确性依据。>

最后总结：时间复杂度是 <复杂度>，适用条件是 <条件>。这里容易混的是 <一个最相关误区>。
```

## 深度控制

- 深度 1：只讲“解决什么问题、核心直觉、一个下一步问题”，不展开完整算法。
- 深度 2：增加维护状态和一个完整小例子，不给完整代码。
- 深度 3：在深度 2 的基础上给伪代码或不超过 15 行的核心片段。
- 深度 4：只有用户明确要求实现时才给代码骨架或完整实现。

学生只是说“看不懂”时，优先使用深度 1 或 2。学生追问“具体怎么走”时，再逐步展示完整状态变化。

## 对比类问题

学生混淆两个算法时，不要分别背诵两段定义。先指出两者共同点，再对比：

1. 目标分别是什么；
2. 每一步选择依据是什么；
3. 维护的状态是什么；
4. 适用条件是什么；
5. 在同一个小例子上会得到什么不同结果。

## 必须避免

- 不要只给定义和复杂度。
- 不要一开始就粘贴完整代码。
- 不要用更难的术语解释当前术语；必须先解释新词。
- 不要省略算法的适用条件，例如 Dijkstra 的非负边权条件。
- 不要混用不同教材的下标约定，例如 KMP 的 `next` 与 LPS。
- 不要把一种实现的中间数组或划分结果说成所有实现唯一的结果。
- 不要编造例子结果；给出前先手算验证。
