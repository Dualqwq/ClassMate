## 本轮关键修改

1. Router 和 Planner 合并为一次 `RouteAndPlan` 调用。
2. RouteAndPlan 只接收精简后的完整 `SKILL.md`、完整紧凑 Skill 目录、问题和压缩工作区目录，不读取文件正文。
3. RouteAndPlan 改用短字段 JSON；可选字段缺失时本地补默认值，数组过长时安全截断。
4. DeepSeek 规划调用关闭思考模式，最大输出限制为 500 tokens。
5. Answer 仍提交精简后的完整 `SKILL.md`，并只补充被选中的 Skill 小节和工作区文件。
6. Answer 强制走流式适配器；ChatSession 不再在结束事件中重复追加完整回答。
7. 明确要求第一层提示时，本地锁定 `problem_hint`，限制回答长度和代码行数；浅层提示关闭思考模式，最大输出限制为 700 tokens。
8. 每次请求记录各节点耗时、首个回答片段时间，以及 RouteAndPlan、Answer 和整次流程的 Token。

- 正确指出从 0 递增的 `n` 永远不会等于 `-1`。
- 正确指出 `current` 最终会成为空指针，并在后续访问中崩溃。
- 只给出补充负下标检查的最小修改方向，没有给完整程序。

结果：通过。

## 用例 3：只给第一层提示

问题：

> 我看不懂 task_list.cpp 里的 insert_after，也不知道内存泄漏怎么修。请只给我第一层提示，不要直接告诉我完整改法或完整代码。

实际回答：

> 好的，我们先聚焦 `insert_after` 和内存泄漏这两个问题，各给一个第一层提示。
>
> 关于 `insert_after`：在纸上画出插入前后的链表连接状态，重点看 `newNode->next = current->next` 和 `current->next = newNode` 的执行顺序。想一想：如果顺序反过来，目标结点原来的下一个结点还能被访问到吗？
>
> 关于内存泄漏：检查 `operator=` 在 `head = copy(other.head)` 之前，原来 `head` 指向的结点是否已经被释放。再想一想 `a = a` 时会发生什么。

结果：通过。回答没有给出完整替换代码；针对用户同时点名的两个问题，各给了一个检查点和引导问题。

## 仍需关注的小问题

1. API 首片段时间受 DeepSeek 服务端和网络波动影响；即使客户端正确使用流式接口，也可能较晚收到第一块。
2. Answer 仍是最大耗时环节。后续若继续优化，应优先压缩 Answer 上下文和回答预算，而不是继续压缩毫秒级的本地节点。
3. 测试使用的 VS Code Insiders 会输出 Mermaid API proposal、GitHub token 和 Node `url.parse()` 的宿主环境警告；这些警告不来自 ClassMate 源码，不影响 150 个测试通过。
4. 仓库当前统一性换行设置不明确，Git 会提示部分 LF 文件将来可能转换为 CRLF；不影响运行，但建议以后增加 `.gitattributes` 后统一处理。
